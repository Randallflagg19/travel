преждевременен. Ниже — замечания статического review и условия допуска к релизу.

## Замечания, требующие действий

### P1 — Первый backend deploy несовместим с каталогом current

**Место:** `.github/workflows/deploy-backend-production.yml`, строки 69–88.

Workflow запоминает предыдущий релиз только для symlink. При существующем
каталоге `current` команда `ln -sfn` создаёт ссылку внутри него, не заменяя
каталог. Сервис может продолжить запускать старый код и успешно пройти
`/health`. Цель автоматического rollback при этом не сохранена.

- [ ] Определить фактическую production backend-версию и сохранить старый
  артефакт как конкретную цель восстановления.
- [ ] Подготовить отдельный переход со старого каталога на release-схему,
  сверив реальный systemd unit и `ExecStart`.
- [ ] Добавить отказ workflow при неожиданном типе `current` и проверку
  фактически активированного релиза.
- [ ] Проверить сценарии успешного переключения и восстановления.

### P1 — Схема БД не проверяется до переключения backend

**Места:** `backend/src/db/db-migrations.service.ts:15`,
`backend/src/db/migrations.ts:156`,
`.github/workflows/deploy-backend-production.yml:79`.

Миграции запускаются при старте только с `DB_MIGRATE_ON_START=true`. Новые DDL
добавляют поля и пересоздают constraint `posts_media_type_check`, требуя
блокировки таблицы. Такой старт уже задерживался на staging, что описано в
roadmap. При выключенных миграциях `/health` может пройти без нужной схемы:
этот endpoint возвращает константный успех. Production ожидает 15 попыток,
staging — 120.

- [ ] Проверить реальную production-схему и значение `DB_MIGRATE_ON_START`.
- [ ] Подготовить отдельный управляемый шаг применения/проверки схемы до
  переключения сервиса, с ограничением ожидания блокировок.
- [ ] Проверить резервную копию и порядок восстановления, совместимость
  предыдущего backend с расширенной схемой.
- [ ] Дополнить приёмку проверкой БД, необходимых колонок/constraints и
  API-контрактов. Один `/health/db` тоже не доказывает наличие нужных колонок.

Простое увеличение таймаута deploy не заменяет управление миграциями.

### P1 — Grid не резервирует полную высоту историй и комментариев

**Места:** `frontend/src/features/feed/ui/feed-masonry-item.tsx:58`,
`frontend/src/features/feed/ui/feed-post-card.tsx:182` и `:325`.

Расчёт row-span учитывает пропорции и фиксированный footer, но не состояние
раскрытых комментариев и не `min-h-80` истории. Например, при mobile-колонке
170px Grid резервирует истории около 228px при минимальной высоте 320px.
Комментарии добавляются в обычный поток без увеличения занимаемых строк.
Содержимое может перекрываться следующей карточкой в той же колонке.

- [x] Согласовать резерв Grid с минимальной высотой истории и ограниченной
  высотой раскрытого блока комментариев через данные и состояние.
- [x] Не возвращать DOM-измерения и `ResizeObserver` карточек.
- [ ] На узком экране проверить историю и длинные комментарии над следующими
  карточками, включая mixed-ленту и featured.

Это не принятые свободные «карманы» и не проверка второго scrollbar.

### P2 — Ответ PATCH сбрасывает реакции в UI

**Места:** `backend/src/posts/posts.service.ts:399`,
`frontend/src/features/feed/ui/feed.tsx:201` и `:220`.

PATCH возвращает нулевые `like_count`/`comment_count` без `liked_by_me`.
Frontend целиком заменяет карточку этим ответом. После изменения текста или
размера исчезают счётчики и активное сердечко до повторного получения ленты;
следующий клик по уже поставленному лайку отправляет добавление вместо снятия.
Сами реакции в БД не удаляются.

- [ ] Обновлять только изменённые поля кэша либо возвращать полноценный пост
  с актуальными реакциями пользователя.
- [ ] Проверить редактирование и featured на посте с лайком текущего
  пользователя и ненулевым количеством комментариев, затем снятие лайка.

### P2 — Optimistic rollback восстанавливает всю старую ленту

**Место:** `frontend/src/features/feed/ui/feed.tsx:175`; аналогично обработчики
metadata/layout.

При ошибке восстанавливается полный снимок страниц до операции. Параллельные
действия разрешены: если B успешно завершилась после начала A, ошибка A
отменит отображение результата B. Восстановление снимка также может убрать
подгруженную страницу. Согласование с сервером после rollback отсутствует.

- [ ] Откатывать только затронутый пост/поля с учётом более поздних операций;
  согласовывать кэш с сервером после завершения.
- [ ] Проверить две операции с ошибкой одной и подгрузку страницы во время
  ожидающей операции.

### P2 — Production frontend проверяется раньше готовности Next.js

**Место:** `.github/workflows/deploy-frontend-production.yml:73`.

Сразу после restart выполняется единственный `curl`. Для `Type=simple`
успешный restart не означает готовность порта. Исправный релиз может быть
откачен при обычной задержке запуска. `--max-time 5` не помогает при немедленном
отказе соединения. На staging уже есть цикл ожидания.

- [ ] Добавить ограниченное ожидание готовности по staging-схеме.
- [ ] Проверять готовность восстановленного сервиса после rollback.

## Обязательные проверки данных и окружения

- [ ] Закрыть условие roadmap по внешнему TLS-инциденту: зафиксировать состояние
  внешнего HTTPS и понятный порядок восстановления. Единичный `200` не доказывает
  устранения периодического сбоя. Не перезапускать работающий Nginx ради review.
- [ ] Сверить реальные systemd/Nginx/env: production/staging сервисы, порты,
  `ExecStart`, API URL, CORS, Neon branch и sudo-права. Не выводить секреты в отчёт.
  Репозиторный staging API Nginx — исходный HTTP-шаблон с последующим Certbot,
  а не полный снимок серверного HTTPS.
- [ ] Проверить production `media_width`/`media_height`: отсутствующие и
  неполные пары, записи без `cloudinary_public_id`, необработанные и
  отмеченные как недоступные медиа.
- [ ] Подготовить отдельный план production backfill при необходимости.
  Завершение staging backfill не означает заполнения production. Текущая
  реализация пакетная и не ставит отметки при исключении Cloudinary;
  `hasMore: false` означает конец выборки кандидатов, а не размеры у всех постов.
  Reset ранее отмеченных записей не запускать без установленной причины.
- [ ] На staging создать новые фото и видео; проверить обе размерности в БД
  и API, title/text, место и сохранение после refresh, в том числе на mobile.
- [ ] Для upload/delete smoke использовать только тестовые Cloudinary-ресурсы.
  Копия Neon не изолирует файлы: удаление поста вызывает Cloudinary destroy
  по `public_id`. Не удалять скопированные production-медиа из staging.

## Финальная приёмка и порядок релиза

- [ ] Исправить замечания выше и повторить адресные staging-проверки.
  Незакрытые P2 явно согласовать как исключения, если решено выпускать с ними.
- [ ] Повторить короткий smoke итогового кандидата: reload, scroll/пагинация,
  страны/города, featured туда и обратно, история и её редактор, комментарии,
  лайки, upload; desktop и mobile. Проверить отсутствие перекрытий, дёргания
  и второго scrollbar.
- [ ] Зафиксировать проверенные SHA frontend/backend и конкретные предыдущие
  артефакты для rollback. Не считать название ветки доказательством версии.
- [ ] Принять проверенные изменения в `main` и просмотреть итоговый diff.
  Production не выкатывать напрямую из staging-ветки.
- [ ] После отдельного разрешения на production-релиз выполнить подготовленный
  шаг схемы, backend deploy и его проверки; только затем frontend deploy.
- [ ] Проверить фактические активные версии, внешний API/DB health, frontend
  и короткий пользовательский smoke. При неуспехе использовать заранее
  подготовленные цели rollback и проверить восстановление.

Этот документ не является разрешением запускать deploy, миграции или backfill.

## Что не считать новыми багами этого review

- Визуальное переупорядочивание `Grid dense`, включая перенос featured.
- Небольшие вертикальные свободные «карманы» без наложения карточек.
- Временные две mobile-колонки и отсутствие observer-измерений карточек.
- Отсутствие featured-переключателя у историй.
- Отложенное повышение качества preview и доступ к оригиналам.

Мобильное меню `⋮`, caption поверх видео и клавиатурная перемотка уже описаны
в roadmap как незавершённая работа. Они не являются новыми находками этого
review и не должны незаметно расширять объём подготовки релиза.
