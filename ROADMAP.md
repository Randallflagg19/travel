# Travel: актуальный roadmap

Обновлено 2026-09-15. Это единственная точка входа для следующей работы.
Подробные журналы миграций и принятых UI-решений остаются в тематических
документах как архив, а не как текущие инструкции.

## Текущее состояние

- Backend работает на VPS: `https://api.tapir.su/api`.
- Frontend работает на VPS: `https://www.tapir.su`; `https://tapir.su`
  канонически перенаправляется на `www`.
- `https://staging.tapir.su` и `https://api-staging.tapir.su/api` — изолированная
  площадка для проверки будущих релизов. На VPS это отдельные systemd-сервисы,
  порты, release-директории и env-файлы; staging API подключён к Neon branch
  `staging`, а не к production-базе.
- Neon остаётся базой данных, Cloudinary — хранилищем медиа. Для текстовой
  истории Cloudinary не используется.
- Пользовательская приёмка production пройдена на Mac и iPhone, с VPN и без
  него, по Wi-Fi и мобильной сети: просмотр ленты, выбор мест, вход, upload,
  admin-удаление, лайки и комментарии работают.

## Staging-инфраструктура — готова

Изолированная тестовая среда уже создана и проверена. В ней можно свободно
разрабатывать локально, выкатывать выбранный Git ref на staging, создавать
тестовые истории и проверять полный путь до интерфейса, не трогая production.

### Рабочая схема

```text
локальная ветка → GitHub Actions (ручной запуск) → staging frontend :3021
                                                     ↓
staging.tapir.su ───────────────────────────→ api-staging.tapir.su/api :3011
                                                     ↓
                                           отдельная Neon staging branch/DB

main / production → отдельный production backend → api.tapir.su/api → Neon production
```

### Миграции базы и deploy — принятое правило

- **Исправлено 15 сентября на staging.** Backend-релиз `038c155` добавлял
  техническое поле `posts.media_dimensions_checked_at`. Автоматическая миграция
  при старте приложения ждала блокировку таблицы `posts`, из-за чего API не
  успевал открыть порт до health-check, а deploy корректно откатывал релиз.
  Колонку один раз добавили напрямую в Neon SQL Editor для branch `staging`;
  после этого deploy прошёл.
- Для разовых служебных работ с существующей staging-базой допустимо сначала
  применить короткую идемпотентную SQL-миграцию в Neon, а затем выкатывать код.
  Это не меняет пользовательские данные и позволяет отделить ожидание DDL-lock
  от запуска приложения.
- Долгосрочно не полагаться на «миграции во время старта Nest». Нужен отдельный
  управляемый migration-шаг в pipeline: применить/проверить схему, затем
  переключить release и ждать health-check. Ручной SQL Editor остаётся понятным
  аварийным инструментом для staging, а не постоянной заменой процесса.
- **Backfill размеров завершён 15 сентября на staging.** Первые ~510 медиа
  успешно получили размеры, но затем старая реализация исчерпала лимит Admin
  API Cloudinary и ошибочно записала временный отказ как `unavailable`.
  Исправление заменило один запрос на файл пакетами до 100 `public_id`, а
  временные/API-сбои больше не получают финальную отметку. После одноразового
  reset 1\u202f205 ошибочно отмеченных записей повторный backfill обработал 13
  порций: последняя вернула `scanned: 5, updated: 5, unavailable: 0,
  hasMore: false`. Размеры доступны для всех найденных старых staging-медиа;
  регулярно запускать эту процедуру не нужно.

- Staging и production используют разные systemd-сервисы, порты, env-файлы,
  API-домены и базы/ветки Neon. Это относится к **обоим** слоям — frontend и
  backend.
- Cloudinary folder-prefix для staging **ещё не создавался**. Это полезная
  изоляция тестовых медиа, но не блокер текущей задачи с title/описанием:
  истории вообще не используют Cloudinary, а staging уже безопасно отделён по
  API, сервисам и Neon-базе.
- Секреты не попадают в Git: они остаются в GitHub Secrets и env-файлах VPS.
- Первый workflow остаётся ручным (`workflow_dispatch`), без deploy на каждый
  push. Production запускается только после явной приёмки staging.

### Открытый инфраструктурный инцидент — внешний HTTPS/TLS

#### Первый приоритет утром 14 сентября — восстановить Gustaw

- **Выполнено 14 сентября.** HTTPS-vhost и Node-приложение Gustaw были здоровы:
  локальный HTTPS-запрос возвращал `200` и страницу Next.js. Проблемой был
  только HTTP-блок: запрос к `/` отдавал стандартный файл Nginx вместо
  переадресации. В HTTP server block добавлен `return 301
  https://$host$request_uri;`; `nginx -t` прошёл, конфигурация применена через
  `reload`. Локальная проверка с `Host: gustaw.ru` и внешняя проверка подтвердили
  `HTTP 301 → https://gustaw.ru/` и `HTTPS 200`.
- После осознанного `sudo systemctl restart nginx` Tapir production/staging и
  Table Booker снова стали отвечать снаружи (`200` на frontend и API). Но
  `gustaw.ru` показывает стандартную страницу **Welcome to nginx!**. Это
  означает, что сам Nginx работает, однако запрос к этому домену попадает в
  default server, а не в vhost Gustaw. Это **не доказательство проблемы со
  старой Node.js**: Node вообще ещё не участвовал в этом запросе.
- До любых рестартов проверить конфигурацию и включение vhost: `sudo nginx -T
  | grep -ni -C 3 gustaw`, `ls -l
  /etc/nginx/sites-enabled/`, затем сверить `server_name gustaw.ru
  www.gustaw.ru`, `root`/`proxy_pass` и сертификат. После точечного исправления
  — `sudo nginx -t`, затем `sudo systemctl reload nginx` (reload, а не restart)
  и внешний HTTPS-check. Не трогать Node-сервис, пока vhost не начал
  проксировать запросы к нему.
- Утренний контроль: открыть `www.tapir.su`, `staging.tapir.su`, Table Booker
  и `gustaw.ru`; если первые три доступны, а Gustaw снова показывает default
  page, диагностировать только конфигурацию Gustaw. Не выкатывать production
  Tapir, пока не понятна причина общего внешнего TLS-сбоя.

- 13 сентября повторился инцидент, который одновременно затрагивает staging и
  production: HTTP на `80` отвечает `301`, TCP к `91.210.170.148:443`
  устанавливается, но внешний TLS handshake периодически зависает или
  обрывается. Из-за этого сайт может бесконечно показывать стартовую загрузку,
  хотя UI и API-логика исправны.
- Локальная диагностика VPS: Nginx, `travel-frontend` и
  `travel-frontend-staging` были `active`; frontend на `127.0.0.1:3020` и
  `:3021` отдавал `200`; локальный TLS для всех четырёх доменов отвечал;
  `nginx -t` успешен. Это не проблема изображений, базы или frontend-кода.
- **Срез после сбоя 14 сентября, 09:12:** после перезапуска Nginx все три
  независимых сайта снова получили внешний `200`. На VPS нет признаков
  исчерпания ресурсов: всего 42 TCP-сокета, 2688 файловых дескрипторов при
  системном лимите около `9e18`, Nginx занимает около 3.3 MiB; в kernel journal
  нет OOM или сетевой ошибки. Сообщения `[UFW BLOCK]` — обычные сканы случайных
  закрытых портов, а error log Nginx — запросы ботов к несуществующим
  WordPress/.git-файлам; они не объясняют закрытие HTTPS для всех доменов.
  Этот срез не доказывает корень: он снят уже после restart, который сбросил
  живое состояние Nginx.
- Поведение на iPhone различается между Wi-Fi, мобильной сетью и VPN, но это
  не опровергает внешний TLS-сбой: все домены используют один VPS и общий
  Nginx. Не делать вывод, что виноват конкретный провайдер, пока не собраны
  nginx journal/error logs во время сбоя.
- При следующем воспроизведении: снять read-only snapshot из
  `infra/travel-frontend/diagnose-https-incident.sh`; если `nginx -t` успешен,
  локальные сервисы здоровы, а TLS извне всё ещё не работает, допустимо
  `sudo systemctl restart nginx`, затем проверить все frontend/API домены
  снаружи. Перед restart приоритетнее снять 30-секундный `tcpdump` на `443` и
  одновременно сделать контролируемый внешний HTTPS-запрос: если пакеты не
  приходят на VPS или ответные пакеты не уходят, это доказательство для
  обращения к хостеру; если handshake приходит и обрывается на VPS, проверять
  Nginx/ядро. Это отдельная эксплуатационная задача и блокер production-релиза.
  `gustaw-vps` — только локальный SSH-алиас на Mac для
  `tapiradmin@91.210.170.148`, исторически названный по другому проекту; это
  не сайт и не сервис на VPS. Команду `ssh gustaw-vps` выполняют на Mac, чтобы
  войти на сервер, а не внутри уже открытой SSH-сессии. `restart nginx` —
  общий перезапуск reverse proxy для всех сайтов VPS: он не перезапускает их
  application-сервисы и не меняет данные, но кратко прерывает HTTP/HTTPS для
  всех vhost. Не запускать его, пока сайты работают; после осознанного
  перезапуска проверить `sudo systemctl is-active nginx` и внешний HTTPS.
- **Маршрутная диагностика по запросу хостера:** пока сайт доступен, ничего не
  запускать. При следующем сбое до restart Nginx на Mac в проблемной сети
  зафиксировать время и публичный IPv4, затем выполнить ICMP- и TCP/443-MTR до
  `91.210.170.148` (по 100 проб). После этого на VPS выполнить обратный MTR к
  зафиксированному IPv4. Полные команды намеренно выдавать пользователю только
  в момент сбоя, чтобы не смешивать baseline со свидетельством инцидента.

### Текущий incident-response — production frontend `504`

- **Наблюдение 13 сентября, 22:41:** `tapir.su` отдаёт `504 Gateway Time-out`
  от `nginx/1.24`, тогда как `staging.tapir.su`, Gustav и Table Booker доступны.
  Это не равнозначно падению VPS или Nginx: `504` означает, что Nginx принял
  запрос, но не получил своевременный ответ от upstream. Рабочий staging
  использует отдельный `travel-frontend-staging.service` на `127.0.0.1:3021`;
  production использует `travel-frontend.service` на `127.0.0.1:3020`.
- **Цель:** собрать доказательства до восстановления и перезапустить только
  минимально необходимый сервис. Не перезапускать общий Nginx первым действием
  и не выкатывать новый код/production release для исправления incident.
- **План после явного подтверждения пользователя:**
  1. Снять read-only snapshot: `systemctl is-active` для Nginx и обоих
     frontend-сервисов; `curl` к `127.0.0.1:3020` и `:3021`; `ss` listener'ов;
     свободные RAM/disk; последние журналы `travel-frontend` и production
     nginx-vhost.
  2. Если `:3020` не отвечает или production service не active, а `:3021`
     здоров, выполнить только `sudo systemctl restart travel-frontend.service`.
     Это кратко затронет Tapir production, но не staging, Gustav, Table Booker
     или общий Nginx.
  3. Проверить local `:3020`, внешний `https://www.tapir.su/` и
     `https://api.tapir.su/api/health`. Зафиксировать результат в roadmap.
  4. Если restart не помог, не делать каскадных рестартов: читать journal,
     проверить release/current symlink и только затем обсуждать rollback
     production frontend к предыдущему release. Общий Nginx рассматривать
     лишь если перестанут работать несколько vhost или повторится отдельный
     TLS-symptom.
- **Восстановление выполнено 13 сентября, 23:xx.** Диагностика показала:
  `travel-frontend.service` был `active`, но `curl` к `127.0.0.1:3020`
  стабильно зависал; staging `:3021` отвечал `200`, а Nginx в error log
  фиксировал `upstream timed out` для `127.0.0.1:3020`. Выполнен точечный
  `sudo systemctl restart travel-frontend.service`; сразу после команды порт
  ещё мог кратко не слушать, пока Next.js запускался. Затем UptimeRobot прислал
  `Resolved`, а внешний smoke подтвердил `200` для production frontend/API и
  staging frontend/API. Другие приложения и общий Nginx не перезапускались.

- `systemctl cat travel-backend.service` показал реальную конфигурацию:

  не интерпретирован как часть приложения и не должен попадать в новый релиз
  автоматически.
- `du` и `df` показали: runtime занимает около 253 МБ, включая 251 МБ
  `node_modules`; на диске доступно около 7 ГБ из 30 ГБ. Места достаточно,
  чтобы сначала сохранить неизменяемую копию реально работающего legacy
  runtime и получить конкретную цель первого rollback.
- Локальные запросы к `/api/health` и `/api/health/db` вернули `{"ok":true}`;
  сервис находится в состоянии `active/running`, используется Node
  `v22.23.2`. Это подтверждает текущую работоспособность, но не доказывает,
  что будущий release активирован и что в БД присутствует вся требуемая схема.
- `sudo -n -l` показал отсутствие беспарольного права на restart production
  `travel-backend.service`. Поэтому текущий GitHub Actions workflow при первой
  попытке остановится на `sudo systemctl restart`, даже до риска ложного
  health-check. Перед deploy требуется установить уже подготовленное узкое
  sudoers-правило только для нужных команд production backend.
- `journalctl` подтвердил, что при каждом старте Nest выполняет миграционный
  этап и после него успешно открывает приложение. Одновременно обнаружены семь
  внешних завершений процесса через `SIGKILL` с последующим автоматическим
  restart от systemd. Они происходят в моменты, кратные пяти минутам; в kernel
  journal вокруг последнего случая нет признаков OOM. Это похоже на отдельный
  cron/timer/watchdog, а не на штатный restart или исключение Nest; источник
  ещё нужно определить до production deploy.

**Принятый безопасный порядок перехода:** сначала найти источник `SIGKILL`;
сохранить текущий `dist`, `node_modules` и runtime-файлы как именованный
`releases/legacy-0ad47ea-20260915` без копирования секретов; создать symlink
`current` на эту копию; переключить реальный systemd unit с `backend` на
`current`, сохранив отдельный путь к `backend/.env`; перезапустить тот же
старый код и проверить оба health endpoint. Только после успешной миграции
инфраструктуры исправлять workflow и выкатывать новый backend. Workflow должен
отказывать при неожиданном типе `current`, проверять точную цель ссылки и
фактически активный release, а rollback — возвращать сохранённый legacy release
и повторно проверять его здоровье.

9. **Продвинуть принятую версию в production.** После устранения или понятного
   восстановления TLS-инцидента: принять проверенную ветку
   `staging-infrastructure` в `main`, просмотреть итоговый diff, затем вручную
   запустить production backend workflow и только после его health-check —
   production frontend workflow. Проверить `api.tapir.su/api/health` и короткий
   пользовательский smoke на `www.tapir.su`. Для rollback повторно выкатить
   предыдущий принятый Git ref; production не деплоить напрямую из staging-ветки.

## Следующий дизайн-этап — Masonry-лента и выделенные кадры

- Перейти от одинаковых карточек с фиксированными `aspect-ratio` и
  `object-cover` к адаптивной Masonry-сетке: фотографии и видео показываются в
  исходных пропорциях, без обрезания важных частей кадра.
- **Исходная база (15 сентября; подтверждена на staging):** CSS Grid с
  `grid-auto-flow: dense`, тремя колонками на desktop и временно двумя на
  mobile. Обычные карточки получают row-span из сохранённых пропорций
  `media_width`/`media_height`; `FEATURED` занимает две колонки на desktop и
  всю mobile-сетку. Перезагрузка, долгий scroll, подгрузка страниц,
  переключение стран/городов, создание/удаление комментариев и смена размера
  карточек прошли без второго scrollbar и без observer'ов на карточках.
- Поздние посты могут визуально заполнять свободные места; строгая
  хронология на экране намеренно не гарантируется. При увеличении карточка
  может переехать в более подходящую свободную позицию — это принятое
  следствие плотной Grid-раскладки, а не ошибка.
- **Принятый компромисс по вертикальным промежуткам:** у Grid задан одинаковый
  desktop-gap в обеих осях (16px). Для более точного соответствия известной
  высоте кадра шаг неявных строк уменьшен с 8px до 4px. Это сократило лишний
  воздух и прошло staging-проверку без второго scrollbar. Однако `Grid dense`
  иногда оставляет свободные вертикальные «карманы» рядом с карточками разной
  высоты; это не дополнительный CSS-gap и не ошибка данных. Не пытаться
  убирать их DOM-измерением или уменьшением резерва с риском наложения
  карточек. Идеально равный вертикальный ритм потребует отдельного настоящего
  Masonry-алгоритма, особенно сложного из-за `FEATURED` на две колонки,
  историй и комментариев; до отдельного решения текущий вариант принят.
- **Адаптивная композиция реализована локально 15 сентября; ожидает staging-приёмку:**
  - телефон `<640px`: одна колонка; все фото, видео и истории занимают всю
    ширину;
  - планшет `640–1023px`: две колонки; фото и видео занимают одну колонку,
    история — обе;
  - desktop `≥1024px`: три колонки; история остаётся в одной колонке, а для
    фото и видео сохраняются `STANDARD` и двухколоночный `FEATURED`;
  - действия «Сделать крупным» / «Обычный размер» показывать только на
    desktop. На телефоне и планшете в меню оставлять «Редактировать» и
    «Удалить»;
  - одновременно может быть открыто только одно меню `⋮`; клик вне меню и
    `Escape` закрывают его, а позиционирование не должно выводить панель за
    границы viewport;
  - не пытаться автоматически определять «важность» вертикальных фотографий
    и не добавлять crop или ограничение высоты: на первом шаге сохранять
    исходные пропорции. Возможное ручное кадрирование конкретного поста
    обсуждать отдельно только после mobile-проверки.
  - Локальные browser-тесты на viewport `390×844` и `1440×1000` подтверждают
    нужные span, отсутствие управления размером на телефоне, его наличие на
    desktop, единственность открытого меню и закрытие по `Escape`. Фактическую
    приёмку на iPhone и desktop провести после отдельного staging deploy.
  - **Композиция подписей принята и реализована локально:** на телефоне и
    планшете название и описание остаются поверх нижней части кадра, чтобы не
    увеличивать высоту карточки; нижний градиент дополняется мягкой двухслойной
    тенью текста для читаемости на светлом и тёмном фоне. На desktop подпись
    остаётся в отдельной зоне под медиа. Шрифт, размеры и расположение не
    менять; контур (`text-stroke`) не добавлять.
  - Фото и видео во всех режимах сохраняют исходные пропорции: нижняя часть
    desktop-кадра не обрезается, несмотря на визуальный переход к тёмному
    footer. Не вводить `object-cover`, автоматический crop или эвристику
    «важности» вертикальных фотографий.
- Добавить в данные медиа-поста постоянный layout-признак, начав с двух
  состояний: `STANDARD` и `FEATURED`. Он хранится и меняется через API, поэтому
  выбор переживает refresh, другой браузер и staging/production deploy.
- В меню `⋮` фото/видео добавить действие «Сделать крупным»; для выделенного
  поста — «Обычный размер». Истории остаются отдельным paper-форматом и в
  первом шаге не получают этот переключатель.
- Целевая desktop-сетка состоит из трёх колонок; `FEATURED` занимает две и
  получает больше визуального воздуха. На телефоне все карточки полноширинные,
  на планшете действует отдельная двухколоночная композиция, описанная выше.
  Высота всегда следует реальному кадру, а не создаётся crop-ом ради условного
  блока «2×2».
- Для стабильной раскладки без layout shift передавать вместе с медиа реальные
  `width` и `height` оригинала (получать при upload/import и хранить в посте).
  Grid рассчитывает spans из этих сохранённых данных, а не из размеров DOM.
- **Визуальный ритм — отдельная небольшая полировка:** привести внешние
  отступы ленты к одному правилу: слева/справа и сверху/снизу использовать
  согласованный размер, а не оставлять слишком большой разрыв между hero-блоком
  и первой строкой Grid. Менять только spacing контейнеров, не трогая расчёт
  Grid и не возвращая измерения карточек.

### Условия перед переносом Masonry в production

- Staging принял основную ленту: reload, долгая прокрутка, пагинация,
  переключение стран/городов, `FEATURED`, комментарии и удаление комментария
  работают без дёргания и второй полосы прокрутки.
- До production зафиксировать фактические SHA последнего production frontend и
  backend deploy, а не полагаться только на указатель ветки `main`.
- Провести короткий review diff `main...staging-infrastructure` тремя
  независимыми блоками: (1) фронтенд и пользовательские сценарии, (2) backend,
  миграции и Cloudinary-размеры, (3) staging/production workflow, systemd и
  Nginx. Это большой накопленный diff, а не одна визуальная правка.
- Перед запуском production вручную проверить создание нового фото и видео:
  размер должен прийти из Cloudinary и сохраниться в `media_width`/
  `media_height`. После реализации отдельно проверить согласованные mobile и
  desktop-композиции; планшетную версию допустимо принять следующим прогоном.

## Ближайшая приоритетная задача — быстрый полноэкранный просмотр фотографий

Превью в ленте сейчас загружаются быстро, но открытие фотографии на телефоне
может долго ждать более качественный файл. Нужен отдельный полноценный режим
просмотра, одинаково доступный на телефоне и desktop, без ухудшения скорости
первоначальной загрузки Masonry-ленты.

- Нажатие на фотографию открывает её поверх интерфейса на весь доступный экран
  с сохранением пропорций и без crop. Использовать настоящий modal/lightbox с
  корректной блокировкой фоновой прокрутки и доступным состоянием диалога, а не
  временное увеличение самой карточки внутри Grid.
- Повторное нажатие на развёрнутую фотографию закрывает просмотр и возвращает
  пользователя к той же карточке, прежнему размеру и позиции ленты. На
  desktop просмотр также закрывается по `Escape`; необходима явная доступная
  кнопка закрытия для touch, клавиатуры и screen reader.
- В полноэкранном режиме показывать вариант полного качества, а не растягивать
  ограниченное по пикселям превью. При этом не загружать оригиналы всех постов
  вместе с лентой: лента должна продолжать получать оптимизированные
  responsive-превью подходящего размера и формата.
- Перед реализацией проверить текущие Cloudinary URL/transformations и сетевой
  путь при открытии на реальном iPhone и desktop: какой файл запрашивается,
  его размеры, формат, вес, cache headers, время ответа и повторное открытие
  из browser cache. Это отделит задержку загрузки оригинала от задержки UI.
- Предпочтительное направление оптимизации: отдельные URL для preview и
  fullscreen, `srcset`/`sizes` для превью, современный автоматический формат и
  качество на CDN, browser/CDN cache и ограниченный prefetch только вероятного
  следующего действия (например, конкретного изображения при hover/focus либо
  небольшого числа ближайших карточек). Не предзагружать все полноразмерные
  фотографии: это замедлит мобильную сеть и израсходует трафик и память.
- Во время загрузки качественного варианта сразу показывать уже закэшированное
  превью как placeholder, затем незаметно заменить его полноразмерным файлом;
  предусмотреть понятное состояние ошибки и возможность повторной попытки.
- Не смешивать fullscreen с `FEATURED`: «Сделать крупным» меняет композицию
  карточки только в desktop Grid, а fullscreen является временным режимом
  просмотра для любого фото и не изменяет сохранённый layout поста.
- Критерии приёмки: проверка на реальном iPhone и desktop, быстрое визуальное
  открытие из уже показанной ленты, отсутствие скачка/потери scroll position,
  закрытие нажатием, кнопкой и `Escape`, полное качество после догрузки,
  отсутствие массовой загрузки оригиналов и корректное повторное открытие из
  кэша. Отдельно измерить холодное и повторное открытие на быстрой и
  ограниченной мобильной сети.

## Следующая продуктовая задача — довести журнал историй

Текстовые истории являются отдельным типом записи `STORY`: у них есть
`title`, полный `text`, место и реакции. Они входят в общее число постов, но
не создают файл в Cloudinary. Медиа-пост пока содержит ровно один файл — фото
или видео — с необязательной подписью. Фотографии не получают лишнюю плашку,
у видео и историй остаются понятные отметки. Черновик первой истории сохранён в
`design-concepts/story-million.md`.

Согласованные правила данных:

- `posts = photos + videos + stories` (аудио не учитывается в текущем UI);
- backend `/places` возвращает для страны и города `posts`, `photos`, `videos`
  и `stories`;
- API для истории возвращает `media_url: null`; в базе для обратной совместимости
  может храниться пустое техническое значение, но интерфейс его не использует;
- несколько файлов внутри одного поста и отдельная таблица медиа пока **не
  делаются**. Это осознанное будущее расширение, а не текущая миграция.

Дальше:

1. **Название и описание для медиа-постов.** Для фото и видео `title` и `text`
   остаются необязательными. При новом upload сначала открывать компактную форму
   «Название / описание», затем Cloudinary; после успешной загрузки отправлять
   оба поля вместе с URL файла в `POST /posts`. Новая миграция не нужна: поля
   `posts.title` и `posts.text` уже есть.
2. **Редактирование существующих постов.** Добавить защищённый `PATCH /posts/:id`
   с валидацией длины `title` и `text`, доступный администратору. В интерфейсе
   открыть форму через меню `⋮`; она должна позволять добавить или изменить
   название и описание у старых фото/видео, не меняя Cloudinary-файл.
   - Заменить временные браузерные `alert` для ошибок сохранения и удаления на
     единый ненавязчивый UI-статус (toast/сообщение в модалке) с понятным
     текстом и возможностью повторить действие.
3. **Показ метаданных медиа.** На карточке выводить название и короткий фрагмент
   описания; в раскрытом просмотре — полный текст. Пустые поля не создают
   пустых блоков. У истории `title` и полный `text` обязательны, у фото/видео —
   оба поля опциональны.
   - Проверить первое раскрытие комментариев: после нажатия на кнопку карточка
     слегка дёргается. Убрать layout shift, не меняя логику открытия и
     сохранения комментариев.
   - После функциональной приёмки отдельно пройти композицию карточки: добавить
     аккуратный разделитель между title/описанием и нижней панелью реакций,
     чтобы это читалось как две самостоятельные зоны.
   - Переработать расположение полного title/описания в просмотре фото и видео.
     Плашка с заголовком не должна перекрывать кадр или нативные controls
     плеера: сейчас даже короткий title закрывает progress bar. Нужен
     адаптивный caption-panel (отдельная зона рядом/под медиа на desktop и
     компактная зона на mobile), а не текущая плавающая плашка поверх видео.
4. **Masonry-лента — отдельный визуальный этап.** Собрать и сохранить
   референсы в `design-concepts/`, затем адаптировать раскладку карточек без
   изменения API и базы. Проверить desktop/mobile, смешанную ленту фото, видео
   и историй, а также сохранение порядка при пагинации.
5. **Закреплённые посты и истории — следующая UX-задача.** Закреплённые записи
   выводятся перед обычной лентой и сохраняют порядок закрепления. Для первой
   версии управление находится в меню `⋮`: «Закрепить» добавляет пост или
   историю **в начало** списка закреплённых (новое закрепление становится
   первым, прежние сдвигаются ниже), «Открепить» убирает её. Потребуются
   поле состояния и порядка в БД, API и миграция; перетаскивание для ручной
   сортировки не делать на первом этапе, добавить его позже, если простого
   порядка закрепления окажется недостаточно.
   - До реализации проверить, как закреплённые записи сочетаются с Masonry:
     они должны располагаться в отдельной верхней секции, чтобы смена порядка
     не создавала неожиданных скачков по всей обычной ленте.
   - Область закрепления должна храниться отдельно: пост можно закрепить в
     общей ленте и независимо — в ленте конкретной страны/города (папке).
     Первая версия не обязана задавать сложные правила наследования: явно
     выбрать область в действии меню и показывать закреплённые записи только
     в соответствующей верхней секции.
6. **Довести интерактивность Masonry после первой приёмки.**
   - **Мобильное меню `⋮` — выполнено локально 15 сентября.** Старый план с
     панелью только из иконок отменён: после перехода телефона на одну колонку
     помещается понятное текстовое меню «Редактировать» / «Удалить».
     «Сделать крупным» / «Обычный размер» доступно только на desktop.
     Ширина панели ограничена viewport, поэтому она не обрезается.
   - **Единственное активное меню — выполнено локально 15 сентября.** Feed
     хранит id открытой карточки; новое меню закрывает предыдущее. Меню также
     закрывается по `Escape`, клику снаружи и после выбора действия. При смене
     набора карточек старое меню исчезает вместе со своей карточкой.
   - **Сначала вернуть два временно снятых безопасных улучшения.**
     1) Точечный optimistic UI для layout, metadata и delete через
     `setQueryData`, с rollback кэша при ошибке; он делает изменение размера и
     редактирование мгновенными. 2) `React.memo` карточки и стабильные
     callbacks (`useCallback`/`useRef`) для снижения лишних ререндеров.
     Диагностика показала, что ни один из этих двух пунктов не был причиной
     scrollbar: дёргание сохранялось после их отключения.
   - Для финального `FEATURED` добавить `media_width` и `media_height` в БД,
     API и новые upload/import. Затем выполнить idempotent Cloudinary backfill
     размеров для существующих постов. Только после этого сделать Grid-версию
     без `ResizeObserver`: известные пропорции позволят заранее вычислять
     layout и занимать ровно две колонки на desktop.
   - После перехода на Grid отдельно проверить `grid-auto-flow: dense`:
     поздние карточки могут визуально заполнять свободные места. Хронологический
     порядок на экране намеренно не гарантируется; порядок в API и DOM остаётся
     исходным. Проверить mixed-ленту, пагинацию и featured на desktop/mobile.
   - **Не повторять прежнюю схему измерений без отдельной проверки.** Попытка
     заменить постоянные наблюдатели карточек единым `ResizeObserver` на сетке
     и автоматическим пересчётом `grid-row` вызвала кратковременный второй
     вертикальный скролл и заметное дёргание при переходах и загрузке. Изменение
     откатили; причиной признан третий шаг оптимизации Masonry. Если вернёмся к
     экономии наблюдателей, сначала нужен замер/пересчёт без feedback loop между
     высотой grid-строк, шириной viewport и scrollbar, а затем тест на 3G и
     переходах между городами.
   - Вторая попытка — короткий observer на карточке, повторное измерение после
     загрузки медиа и единый обработчик `window.resize` — воспроизвела ту же
     полосу. Её тоже откатили. Текущий Grid обходится без observer'ов на
     карточках; до профилирования не возвращать их ради экономии/уточнения
     высоты, поскольку это не оправдывает визуальную регрессию.
   - Третья попытка — один общий `ResizeObserver` для карточек вместо множества
     отдельных — также воспроизвела кратковременную двойную вертикальную полосу
     при смене страны и позднее при scroll. Эксперимент и все связанные
     workaround-изменения откатить. Задачу «сократить наблюдатели» отложить до
     отдельного профилирования и изоляции scroll-container’ов.
   - Повысить качество preview у `FEATURED`-медиа. Сейчас карточки получают
     общий Cloudinary thumbnail шириной 600px, которого недостаточно для двух
     колонок, особенно на Retina-экране. Добавить responsive `srcSet`/`sizes`
     или отдельный широкий Cloudinary-вариант для featured-карточек; не
     загружать крупные версии для обычных маленьких плиток.
   - Полноэкранный просмотр фото должен открывать полноценный ресурс, а не
     растягивать thumbnail: сейчас изображение заметно теряет качество.
     Спроектировать понятный UX доступа к оригиналу — качественный просмотр с
     zoom и/или контекстное действие сохранения. Отдельная кнопка «Скачать
     оригинал» не обязательна, но исходный файл должен быть доступен без поиска
     URL вручную; учесть размеры файла, загрузку, права доступа и mobile.
   - Измерить фактическое время `PATCH /posts/:id`, `DELETE /posts/:id` и
     ответ Cloudinary/Neon на staging. Отдельно проверить долгий delete видео:
     его Cloudinary-удаление может быть медленнее обычного PATCH, но интерфейс
     не должен выглядеть зависшим.
   - Исправить клавиатуру в раскрытом видео: `ArrowLeft` и `ArrowRight` должны
     перематывать именно открытое видео на небольшой фиксированный шаг, а
     экранные кнопки-стрелки по краям reader-а по-прежнему переключают на
     предыдущий/следующий пост. `Escape` продолжает закрывать reader.
6. **Сначала спроектировать модель данных журнала.** Провести короткое
   исследование похожих travel-journal/фото-дневников и зафиксировать сущности,
   поля и связи до следующих миграций. В частности определить границу между
   медиа-постом с необязательным `title`, текстовой историей, поездкой,
   направлением и местом; решить, какие метаданные нужны сейчас, а какие не
   нужны. Не добавлять галерею до отдельного решения о модели `post_media`.
   Итог — одна согласованная схема и план идемпотентных миграций, а не точечное
   добавление колонок под каждый новый экран.
7. Принять миграцию и проверить публикацию первой истории на staging: desktop,
   iPhone, реакции, комментарии и фильтры по месту.
8. Сделать карту в раскрытой книге данными направления: контур и подсветка
   должны меняться вместе со страной, без хардкод-веток в UI. Для этого хранить
   у направления ключ карты и координату/регион подсветки.
9. Профилировать и ускорить initial/full-size загрузку фотографий при открытии
   и во время scroll, не снижая заметно качество.
10. Определить судьбу счётчиков «кадров» и «видео» в книге: либо сделать их
   настоящими агрегатами по направлению, либо скрыть до появления корректных
   данных.

## Будущий новый VPS и учебный DevOps-этап

- **План:** после приведения текущего проекта в устойчивое и понятное состояние
  выбрать более мощный VPS: ориентир — 40 ГБ диска вместо 30 ГБ и примерно вдвое
  больше RAM, с доплатой около 600 ₽ в месяц. Покупать его заранее не нужно:
  текущая задача — сначала стабилизировать процессы, документацию и staging.
- Новый сервер не копировать побайтно со старого. Данные на текущем VPS могут
  считаться потенциально скомпрометированными; критичных и незаменимых данных
  там нет. Новый VPS развернуть с чистого листа: обновлённая ОС, отдельный
  непривилегированный пользователь, SSH-ключи, firewall, nginx, systemd,
  секреты вне Git, backend/frontend release-директории, staging и production.
- Цель переезда — не только сменить ресурс, но и пройти процесс руками и
  освоить базовые практики DevOps: устройство Linux/VPS, сеть и firewall,
  systemd, reverse proxy и TLS, безопасные секреты, deploy/rollback, бэкапы,
  миграции, логи и мониторинг.
- Критерий готовности к переезду: staging стабильно деплоится и откатывается;
  миграции отделены от старта приложения; есть проверенный runbook развёртывания
  и восстановления; известен минимум переменных окружения и DNS-записей;
  production можно воспроизвести на новом VPS без копирования старой машины.

## Сознательно не в ближайшей работе

- Интерактивный год в заголовке направления (например, `Thailand: Pattaya —
  2026`). Сейчас значение не должно получать новые хардкод-ветки: в будущем
  год нужно хранить как редактируемые данные для направления/поездки и выводить
  в UI. Ориентир для начального заполнения: Паттайя, Бангкок, Индонезия и Китай
  — 2026; Египет — 2024. Модель данных и интерфейс управления будут спроектированы
  отдельной задачей; текущий экран пока не менять.
- Вложенные ответы на комментарии. Обычные комментарии, их отображение и
  удаление автором уже работают; replies пока не нужны.
- Автоматический crop и изменение мобильных пропорций карточек. Фото и видео
  сохраняют реальные пропорции; пользователь принял текущую композицию.
- Удаление Vercel-проекта и design-концептов. Vercel сохранён на период
  наблюдения как rollback-вариант; `design-concepts/` — безопасный архив
  референсов, на runtime он не влияет.
