# Travel: актуальный roadmap

Обновлено 2026-09-12. Это единственная точка входа для следующей работы.
Подробные журналы миграций и принятых UI-решений остаются в тематических
документах как архив, а не как текущие инструкции.

## Текущее состояние

- Backend работает на VPS: `https://api.tapir.su/api`.
- Frontend работает на VPS: `https://www.tapir.su`; `https://tapir.su`
  канонически перенаправляется на `www`.
- `https://staging.tapir.su` и `https://api-staging.tapir.su/api` — изолированная
  площадка для проверки будущих релизов. На VPS это отдельные systemd-сервисы,
  порты, release-директории и env-файлы; staging API подключён к Neon branch
  `staging`, а не к production-базе.
- Neon остаётся базой данных, Cloudinary — хранилищем медиа. Для текстовой
  истории Cloudinary не используется.
- Пользовательская приёмка production пройдена на Mac и iPhone, с VPN и без
  него, по Wi-Fi и мобильной сети: просмотр ленты, выбор мест, вход, upload,
  admin-удаление, лайки и комментарии работают.

## Staging-инфраструктура — готова

Изолированная тестовая среда уже создана и проверена. В ней можно свободно
разрабатывать локально, выкатывать выбранный Git ref на staging, создавать
тестовые истории и проверять полный путь до интерфейса, не трогая production.

### Рабочая схема

```text
локальная ветка → GitHub Actions (ручной запуск) → staging frontend :3021
                                                     ↓
staging.tapir.su ───────────────────────────→ api-staging.tapir.su/api :3011
                                                     ↓
                                           отдельная Neon staging branch/DB

main / production → отдельный production backend → api.tapir.su/api → Neon production
```

- Staging и production используют разные systemd-сервисы, порты, env-файлы,
  API-домены и базы/ветки Neon. Это относится к **обоим** слоям — frontend и
  backend.
- Cloudinary folder-prefix для staging **ещё не создавался**. Это полезная
  изоляция тестовых медиа, но не блокер текущей задачи с title/описанием:
  истории вообще не используют Cloudinary, а staging уже безопасно отделён по
  API, сервисам и Neon-базе.
- Секреты не попадают в Git: они остаются в GitHub Secrets и env-файлах VPS.
- Первый workflow остаётся ручным (`workflow_dispatch`), без deploy на каждый
  push. Production запускается только после явной приёмки staging.

### Что уже сделано

1. **Preflight и проектирование — выполнено 9 сентября.** VPS: 8.5 ГБ свободно
   из 30 ГБ, ~952 МБ доступной RAM, swap занят на 1.1 ГБ. `travel-backend` и
   `travel-frontend` active; production API и DB health отвечают `200`.
   Backend занимает ~350 МБ. Порт 3011 свободен и выбран для staging API.
   Важно: `www.tapir.su` и `staging.tapir.su` сейчас направлены на один процесс
   frontend на 3020, поэтому staging frontend пока не изолирован. Сервер имеет
   17 zombie-процессов и 277 доступных обновлений; это не блокирует задачу и не
   является поводом для массовых обновлений/перезапуска в рамках staging.
   У `tapiradmin` без пароля разрешён только restart старого production frontend;
   до первого staging deploy нужно добавить узкие sudo-права исключительно для
   `travel-frontend-staging.service` и проверки/reload nginx, без полного sudo.
2. **Изолировать staging frontend — выполнено 9 сентября.** Создана отдельная release-директория,
   env-файл и systemd unit на `127.0.0.1:3021`. Переключить только nginx vhost
   `staging.tapir.su` на 3021, оставить `www.tapir.su` на 3020. Сначала в новом
   процессе сохраняется production API — это проверяет изоляцию без изменения
   поведения приложения. Подтверждены: оба systemd-сервиса active, оба публичных
   адреса отвечают `200`, TLS-сертификат `staging.tapir.su` валиден. Во время
   переключения в репозиторном nginx-шаблоне обнаружилась устаревшая HTTP-версия;
   полный Certbot HTTPS-конфиг восстановлен и сохранён в репозитории.
3. **Поднять staging backend — выполнено 9 сентября.** Создана Neon branch
   `staging` как копия production без автоудаления. Отдельный backend запущен
   на `127.0.0.1:3011`, использует собственный env, отдельный JWT secret и
   CORS для `https://staging.tapir.su`; его `/api/health` и `/api/health/db`
   отвечают успешно. Применённые миграции относятся только к staging-ветке.
   DNS `A` `api-staging.tapir.su → 91.210.170.148` создан, nginx vhost и TLS
   настроены, публичный API и CORS подтверждены. До публикации тестовых медиа
   остаётся завести отдельный Cloudinary folder-prefix.
4. **Переключить staging frontend — выполнено 9 сентября.** Ему задан
   `NEXT_PUBLIC_API_URL=https://api-staging.tapir.su/api`, выкатить на staging
   и проверить login, ленту, места, upload, likes и comments. Production не
   меняется. Подтверждено: staging release содержит новый API URL; production
   release по-прежнему содержит `https://api.tapir.su/api`.
5. **Сделать backend deploy pipeline — выполнено 10 сентября.** GitHub Actions
   собирает backend в Linux, передаёт версионированный релиз по SSH, переключает
   `current` на новый релиз и ожидает health-check до 30 секунд. При неуспехе
   возвращается предыдущий релиз. Pipeline проверен на staging: активен релиз
   `331351d`, `/api/health` отвечает успешно, `/api/places` отдаёт агрегаты
   фото/видео/историй. Для production подготовлен отдельный ручной workflow,
   но он ещё ни разу не запускался.
6. **Выкатить frontend истории на staging — выполнено 11 сентября.** Workflow
   собрал `staging-infrastructure`, выложил его только в
   `travel-frontend-staging`, перезапустил только staging service и вшил
   `https://api-staging.tapir.su/api`. На staging подтверждено: фотографии без
   бейджа `PHOTO`, видео с бейджем «Видео», доступна кнопка создания истории.
7. **Проверить историю — выполнено 11 сентября.** В staging опубликована
   «Как я потерял миллион в обменнике»: запись сохранилась в Neon staging,
   появилась в ленте и открылась с полным текстом в модальном просмотре.
   Таким образом подтверждён весь путь frontend → staging API → staging Neon →
   frontend. Этот пост намеренно отсутствует на production-сайте.
8. **Довести визуал историй.** Отдельно пройти типографику: масштаб заголовка,
   шрифт и ритм основного текста, межабзацные интервалы, верхний блок с
   местом/датой и карточку истории. Это визуальная задача, не блокирующая
   текущую функциональность.
9. **Выпустить feature.** После приёмки запустить production backend workflow,
   затем production frontend workflow. Отдельно подтвердить health и короткий
   пользовательский smoke на production.

## Следующий этап — названия и описания медиа-постов

Первый шаг сейчас: реализовать title/описание при создании фото или видео и
редактирование этих полей у существующих медиа-постов. Production workflows не
запускать до отдельной приёмки staging.

## Следующая продуктовая задача — довести журнал историй

Текстовые истории являются отдельным типом записи `STORY`: у них есть
`title`, полный `text`, место и реакции. Они входят в общее число постов, но
не создают файл в Cloudinary. Медиа-пост пока содержит ровно один файл — фото
или видео — с необязательной подписью. Фотографии не получают лишнюю плашку,
у видео и историй остаются понятные отметки. Черновик первой истории сохранён в
`design-concepts/story-million.md`.

Согласованные правила данных:

- `posts = photos + videos + stories` (аудио не учитывается в текущем UI);
- backend `/places` возвращает для страны и города `posts`, `photos`, `videos`
  и `stories`;
- API для истории возвращает `media_url: null`; в базе для обратной совместимости
  может храниться пустое техническое значение, но интерфейс его не использует;
- несколько файлов внутри одного поста и отдельная таблица медиа пока **не
  делаются**. Это осознанное будущее расширение, а не текущая миграция.

Дальше:

1. **Название и описание для медиа-постов.** Для фото и видео `title` и `text`
   остаются необязательными. При новом upload сначала открывать компактную форму
   «Название / описание», затем Cloudinary; после успешной загрузки отправлять
   оба поля вместе с URL файла в `POST /posts`. Новая миграция не нужна: поля
   `posts.title` и `posts.text` уже есть.
2. **Редактирование существующих постов.** Добавить защищённый `PATCH /posts/:id`
   с валидацией длины `title` и `text`, доступный администратору. В интерфейсе
   открыть форму через меню `⋮`; она должна позволять добавить или изменить
   название и описание у старых фото/видео, не меняя Cloudinary-файл.
3. **Показ метаданных медиа.** На карточке выводить название и короткий фрагмент
   описания; в раскрытом просмотре — полный текст. Пустые поля не создают
   пустых блоков. У истории `title` и полный `text` обязательны, у фото/видео —
   оба поля опциональны.
4. **Masonry-лента — отдельный визуальный этап.** Собрать и сохранить
   референсы в `design-concepts/`, затем адаптировать раскладку карточек без
   изменения API и базы. Проверить desktop/mobile, смешанную ленту фото, видео
   и историй, а также сохранение порядка при пагинации.
5. **Закреплённые посты — отложенная UX-задача.** Закреплённые записи выводятся
   перед обычной лентой и сохраняют порядок закрепления. Для первой версии
   управление находится в меню `⋮`: «Закрепить» добавляет запись в конец списка
   закреплённых, «Открепить» убирает её. Перетаскивание для ручной сортировки
   не делать на первом этапе; добавить его позже, если простой порядок
   закрепления окажется недостаточным.
6. **Сначала спроектировать модель данных журнала.** Провести короткое
   исследование похожих travel-journal/фото-дневников и зафиксировать сущности,
   поля и связи до следующих миграций. В частности определить границу между
   медиа-постом с необязательным `title`, текстовой историей, поездкой,
   направлением и местом; решить, какие метаданные нужны сейчас, а какие не
   нужны. Не добавлять галерею до отдельного решения о модели `post_media`.
   Итог — одна согласованная схема и план идемпотентных миграций, а не точечное
   добавление колонок под каждый новый экран.
7. Принять миграцию и проверить публикацию первой истории на staging: desktop,
   iPhone, реакции, комментарии и фильтры по месту.
8. Сделать карту в раскрытой книге данными направления: контур и подсветка
   должны меняться вместе со страной, без хардкод-веток в UI. Для этого хранить
   у направления ключ карты и координату/регион подсветки.
9. Профилировать и ускорить initial/full-size загрузку фотографий при открытии
   и во время scroll, не снижая заметно качество.
10. Определить судьбу счётчиков «кадров» и «видео» в книге: либо сделать их
   настоящими агрегатами по направлению, либо скрыть до появления корректных
   данных.

## Очередь после названий

- Профилактически исключить конфликт старого клиентского кэша с новыми Next.js
  Server Actions при следующем релизе. Во время миграции один такой переходный
  случай был, но сервис восстановился после refresh.
- Свести в отдельный технический этап: API-контракты, тесты, auth, миграции и
  декомпозиция сервисов — см. [REVIEW_LEARNING_ROADMAP.md](REVIEW_LEARNING_ROADMAP.md).

## Сознательно не в ближайшей работе

- Интерактивный год в заголовке направления (например, `Thailand: Pattaya —
  2026`). Сейчас значение не должно получать новые хардкод-ветки: в будущем
  год нужно хранить как редактируемые данные для направления/поездки и выводить
  в UI. Ориентир для начального заполнения: Паттайя, Бангкок, Индонезия и Китай
  — 2026; Египет — 2024. Модель данных и интерфейс управления будут спроектированы
  отдельной задачей; текущий экран пока не менять.
- Вложенные ответы на комментарии. Обычные комментарии, их отображение и
  удаление автором уже работают; replies пока не нужны.
- Изменение мобильных пропорций карточек. Фото остаются `3:2`, видео —
  широкими; пользователь принял текущую композицию.
- Удаление Vercel-проекта и design-концептов. Vercel сохранён на период
  наблюдения как rollback-вариант; `design-concepts/` — безопасный архив
  референсов, на runtime он не влияет.
