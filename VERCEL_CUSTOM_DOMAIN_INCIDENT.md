# Недоступность frontend через собственный домен Vercel

Обновлено: 2026-09-07. Период наблюдений: 2026-09-04 — 2026-09-07.

Статус: проблема воспроизведена; точная сетевая причина не установлена.
Выбранное направление: перенос frontend на VPS после UI/мобильных взаимодействий и рефакторинга, по [общему порядку](ROADMAP.md). Перенос пока не выполнен.

Документ хранит наблюдения, а не очередь реализации. Сетевые проверки ниже исторические; при сверке с кодом 7 сентября новые сетевые измерения не выполнялись.

## Конфигурация по журналу наблюдений

- Frontend: Vercel, `https://travel-coral-five-50.vercel.app`.
- Собственный домен: `tapir.su`, перенаправление 308 на `www.tapir.su`; Vercel показывает Valid Configuration.
- DNS в Timeweb: `A tapir.su → 216.198.79.1`, `CNAME www.tapir.su → f5d2dc3ff8378a98.vercel-dns-017.com`.
- Backend: VPS Timeweb `91.210.170.148`, `https://api.tapir.su/api`, systemd-сервис `travel-backend`, внутренний порт 3010.
- База остаётся на Neon, медиа на Cloudinary.
- `NEXT_PUBLIC_API_URL=https://api.tapir.su/api`; CORS backend разрешает оба собственных домена и исходный адрес Vercel.
- История настройки VPS: [VPS_BACKEND_MIGRATION_ROADMAP.md](VPS_BACKEND_MIGRATION_ROADMAP.md).

## Наблюдения и проверки

1. 4 сентября после настройки DNS, HTTPS и CORS приложение работало через собственный домен. Первоначальная ошибка CORS была исправлена отдельно.
2. 5 сентября собственный домен начал медленно загружаться: загрузочный экран, отсутствующие изображения, частично работающий интерфейс. Через адрес Vercel приложение загружалось быстро.
3. В раннем сравнении `www.tapir.su/first-screen/journal-template-clean.png` передал около 184 КБ за 15 секунд, тогда как тот же файл через `vercel.app` загрузился целиком примерно за 1,1 секунды.
4. Последующие проверки с Mac иногда были быстрыми: пользователь получил 1,53 секунды через собственный домен и 0,84 секунды через Vercel. Это не означало устранения проблемы на других сетевых путях.
5. На iPhone через Wi-Fi и сотовую сеть исходный адрес Vercel работал быстро, `/api/health` сразу возвращал `{"ok":true}`, но прямая картинка через `www.tapir.su` зависала. VPN на телефоне не устранил сбой; его маршрутизация не проверена.
6. На телефоне один и тот же PNG через `vercel.app` загружался быстро, а через `www.tapir.su`, включая URL с новым query-параметром, не загружался.
7. Safari Web Inspector показал сбои загрузки JavaScript, шрифтов и изображений с собственного домена. Затем Safari сообщал: «Сетевое подключение было прервано»; консоль: `Failed to load resource: Сетевое соединение потеряно` для `https://www.tapir.su/`.
8. В начале работы инспектор был подключён к Telegram, а не Safari. Пустые таблицы этого этапа не являются доказательством отсутствия запросов. Позже подключение к Safari было исправлено.
9. Mac через режим модема iPhone также воспроизвёл частичную загрузку изображений и проблемы взаимодействия. Сбой не ограничен мобильной версткой или iPhone.
10. В проверке агента 7 сентября оба адреса отдавали PNG целиком примерно за 1,8 секунды: HTTP 200, одинаковые ETag и размер 2 516 987 байт, `x-vercel-cache: HIT`. Эта проверка отражает только доступный агенту сетевой путь.

Ранее HTML двух доменов совпадал, а JS bundle содержал адрес VPS API, не Render. Проверки API возвращали данные и корректные CORS-заголовки. Это не доказывает исправность всех функций приложения, но отделяет наблюдаемый сбой прямой загрузки статического файла от backend и базы.

## Что установлено, а что нет

- Локализована нестабильная доставка frontend через собственный домен на определённых сетевых путях. Обрывы JavaScript могут объяснять зависание и частичную интерактивность.
- Не установлено, виноваты ли фильтрация, маршрутизация, DNS, TLS, HTTP или инфраструктура Vercel. Нельзя утверждать, что доказана блокировка в России.
- В выполненной DNS-проверке AAAA-записей не обнаружено; версия о проблеме IPv6 не подтверждена. Это не проверка DNS всех устройств и операторов.
- Адрес Vercel в среде проверок разрешался в `198.18.157.150`, что может указывать на подстановку адреса VPN/прокси. Поэтому сравнения с Mac нельзя считать измерениями гарантированно одинакового сетевого пути.
- Разные IP сами по себе не доказывают разные географические узлы CDN; заголовки обоих адресов содержали `fra1`.
- Размер изображений не объясняет наблюдаемое различие доменов. Пользователь не хочет сжимать изображения в качестве исправления этого инцидента.
- Ожидание не устранило проблему для телефона. Продолжать проверки инкогнито и ожидание без нового диагностического вопроса нецелесообразно.

## Решение и следующий этап

Пользователь предпочёл направление переноса frontend на VPS обращению в поддержку Vercel. Это обход проблемного пути доставки, а не доказанное исправление первопричины. До испытания нельзя гарантировать результат.

Детали реализации, проверки временного HTTPS-домена, автоматический Git deploy,
переключение DNS и откат ведутся только в
[VPS_FRONTEND_MIGRATION_ROADMAP.md](VPS_FRONTEND_MIGRATION_ROADMAP.md).
Порядок: сначала UI/мобильные взаимодействия, затем рефакторинг, после этого перенос.
Backend уже на VPS; Neon и Cloudinary остаются.

## Требует проверки

Точная сетевая причина и результат переноса на сетях пользователя остаются
неизвестными. Текущие ресурсы сервера, DNS и конфигурацию перед deployment
нужно проверить заново. Успешная загрузка с одного сетевого пути не закрывает инцидент.

В рамках этой документальной сверки код приложения, DNS, сервер и deployment не изменялись.
