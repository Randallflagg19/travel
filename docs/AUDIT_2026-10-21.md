### Первичная загрузка и запросы

1. [Home](../frontend/src/app/page.tsx) содержит клиентский Feed под Suspense, без
   server-prefetch/hydration данных. [useSelectedAuthor](../frontend/src/features/feed/model/use-selected-author.ts)
   требует совпадения author с query-параметром даже после получения default автора.
   В mobile cold: authors начался на 408 мс, завершился около 599 мс; URL/RSC переход
   занял ещё ~903 мс; posts начался только на 1520 мс. Ускорение начинается с устранения
   этого барьера. SSR первой публичной страницы — возможный следующий шаг после замера,
   с отделением персонального liked_by_me от публичного кэша.
2. [fetchPostsPage](../frontend/src/shared/api/api.ts): GET с Content-Type application/json
   вызвал OPTIONS даже у гостя. Удалить ненужный заголовок; у запросов с Authorization
   preflight может оставаться. Один домен/proxy — отдельный выбор, не обязательная миграция.
3. QueryClient без defaultOptions; useQuery без staleTime. После лайка/комментария
   [Feed](../frontend/src/features/feed/ui/feed.tsx):315/357 инвалидирует все posts.
   Накопленная infinite query перечитывает страницы последовательно — это особенно
   дорого после долгой прокрутки. Нужны адресное обновление и стратегия свежести,
   не механическое отключение всех refetch. [TanStack defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults),
   [infinite queries](https://tanstack.com/query/latest/docs/framework/react/guides/infinite-queries).
4. Повторные useSelectedAuthor в header/sidebar/feed используют **одинаковый query key**:
   число вызовов хука не равно числу HTTP-запросов. В cold-прогонах authors запрошен один
   раз. Не переписывать их только ради уменьшения числа hooks.

## Авторы: что правильно, чего не хватает

**Текущий контракт:** все журналы публичны. Фильтр authorId — выбор ленты, не политика
приватности. GET posts без authorId может вернуть публикации разных авторов; GET post
доступен без входа. Это не утечка «приватных» данных: приватных журналов пока нет.

| Роль | Реально разрешено |
| --- | --- |
| Гость | Чтение авторов/постов/комментариев |
| USER | Регистрация, вход, лайки; не публикация и не создание комментария |
| AUTHOR | Свои STORY, изменение/удаление/закрепление своих постов, комментарии только к своим постам, лайки |
| ADMIN | Медиа и управление постами разных авторов; это доверенный администратор |
| SUPERADMIN | То же плюс выдача/отзыв AUTHOR |

Серверные ownership-проверки есть в PostsService, включая SQL-условия записи.
JWT strategy читает актуальную роль из БД: старый JWT не сохраняет отозванный AUTHOR.
Новый пользователь получает USER, password >=8; публичный authors не возвращает email.
Cloudinary endpoints закрыты от AUTHOR, а попытка прикрепить медиа к STORY запрещена.
Это полезная граница первого этапа. Не обходить её выдачей ADMIN.

**Недостающие части полноценного авторского журнала:**

1. Нет photo/video upload AUTHOR, личного media connection, квот и управления хранилищем.
   Весь CloudinaryService использует один глобальный cloudinary.config; текущий unique
   индекс — только public_id. Для нескольких облаков этого недостаточно.
2. Предлагаемая модель для личных Cloudinary: media_connections с owner_id, provider,
   cloud_name, зашифрованными credentials; media_assets с connection_id, asset_id,
   resource_type, public_id, dimensions/status; уникальность в пределах connection,
   а не всего приложения. Credentials задавать в защищённом интерфейсе, не пересылать
   через чат. SDK должен получать credentials конкретного connection на операцию,
   без переключения глобального singleton между запросами пользователей.
3. Более простой продуктовый вариант — единое управляемое хранилище с серверным owner
   namespace и квотами. Выбор зависит от оплаты и удобства onboarding; он ещё не принят
   в этой сессии. Реализовать один вариант, а не оба. Для обоих сервер определяет owner,
   проверяет связь upload с пользователем, разрешённые параметры подписи, тип/размер/квоты.
4. Import требует preview/dry-run, явного выбора владельца и места, идемпотентности,
   прогресса/retry. Сейчас общий admin import последовательно запрашивает metadata,
   включая уже импортированные ресурсы, и привязывает записи к текущему админу.
5. Удаление сейчас вызывает Cloudinary destroy, затем DELETE БД; ошибка облака
   проглатывается. Для нескольких авторов нужен надёжный статус удаления/retry и разделение
   «убрать из журнала»/«удалить исходный файл». Две разные БД не изолируют общий Cloudinary.
6. UI умеет выдать AUTHOR, но не отозвать его, хотя API поддерживает USER. Нет полноценного
   восстановления пароля, onboarding ожидания, собственного профиля/обложки.
7. Отдельной trip нет: owner лежит на posts, country/city — строки. Следующий слой:
   trips(owner_id,title,start/end dates,cover), optional posts.trip_id с проверкой общего
   владельца. Поездки в одну страну в разные годы — разные сущности. Сложные организации,
   совместные роли и private ACL для указанного пользователем сценария не нужны сейчас.

## Контракты, архитектура и тесты

- **Runtime validation — реальный дефект.** TypeScript Body-типы не проверяют JSON.
  Локальный прямой вызов собранных controllers/services с username=123 и text={} дал
  TypeError до обращения к БД; HTTP-слой не имеет общего ValidationPipe. Нужны 400 и
  лимиты полей, включая media create и comments. Cursor проверяет string, но не UUID/date.
- **Auth остаётся MVP.** JWT 30d в localStorage, нет rate limiter в приложении/показанных
  nginx-шаблонах, refresh/session revocation и recovery. Runtime-конфиг Nginx не проверялся,
  поэтому отсутствие внешнего лимита не утверждается. Регистрационные 8 символов уже
  исправлены; login >=3 оставлен для существующих паролей намеренно.
- **zod всё ещё случайная зависимость:** импорт в login/register, нет прямой dependencies,
  lock помечает его dev. Успешная сборка сейчас не закрывает воспроизводимость.
- **Memo карточек частично обесценен:** Feed на каждый render создаёт новый
  onActionsOpenChange для каждой карточки; handleDeletePost зависит от всего items.
  Исправить конкретные нестабильные props, затем профилировать. [React memo](https://react.dev/reference/react/memo).
  useInView/обработка Escape/resize — нормальные внешние подписки с cleanup, их не удалять
  просто ради сокращения эффектов. useFeedPermissions без hooks можно назвать чистым helper,
  но это косметика, не ускорение страницы.
- **Длинная лента:** все страницы остаются в DOM/кэше; нет maxPages/виртуализации. Это
  риск роста, не измеренный сегодня дефицит памяти. Профилировать 100–300 карточек до
  изменения Grid. Не повторять отклонённые observer-эксперименты без доказательств.
- **БД:** pool max=1 сериализует запросы. Не объявлять его причиной текущего cold load:
  API в тёплом прогоне отвечает быстро. Перед увеличением pool — замер concurrency и
  EXPLAIN на копии данных. Индексы user_id и country/city есть; составной индекс под
  author+pin+pagination выбирать по плану запроса. Likes выбираются одним batch для страницы,
  не отдельным запросом на каждый пост.
- **Миграции:** единый idempotent DDL на старте, без version table/отдельной команды;
  DROP/ADD constraint и backfill выполняются повторно. Нужен baseline реальных двух схем
  и migration gate, а не новая ORM ради миграций. DB constraint размеров также стоит
  усилить: SQL CHECK допускает UNKNOWN при одной NULL-размерности.
- **Тесты:** 29 unit-тестов — уже не только Hello World. Есть ownership, role refresh,
  pin/cursor и author list. Но большая часть использует mock SQL/проверку текста запроса,
  не настоящую PostgreSQL. Нет полноценных HTTP/DB регрессий likes/comments/invalid input,
  media permissions, concurrent mutations. Backend e2e всё ещё шаблонный Hello World;
  frontend like-smoke может пройти без клика, если кнопку не нашёл. Deploy workflows
  запускают lint/build, но не эти тесты.
