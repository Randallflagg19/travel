# Устройство и выпуск каруселей

Актуализировано 4 ноября 2026. На staging выпущены бэкенд `57d4dcd` и фронтенд
`a68dd64`. Владелец проверил публикацию и удаление файлов в Cloudinary.
Выпуск на production остаётся отдельным этапом.
Очередь — в [ROADMAP](../ROADMAP.md), объём — в [MEDIA_POSTS](MEDIA_POSTS.md),
оставшиеся технические задачи — в [BACKLOG](BACKLOG.md).

## Устройство

`posts` остаётся публикацией с автором, текстом, местом, датой и реакциями.
`post_media` хранит 1–10 вложений и их позиции. Поля одиночного медиа в `posts`
содержат обложку для совместимости с предыдущей версией. Истории не имеют вложений.

При выборе файлов создаются только локальные превью. После «Опубликовать» сервер
регистрирует `media_sessions` и `media_uploads`, подписывает заранее выделенные
Cloudinary public ID, проверяет реальные метаданные загруженных файлов и сохраняет
одну публикацию со всеми вложениями в транзакции. Повтор публикации с той же
сессией возвращает тот же ID; другое содержимое под тем же ключом отклоняется.
Файлы отправляются из браузера в Cloudinary; локальная БД хранит сведения о них
и ссылки. Страна и город наследуются из текущего раздела журнала.
Общая функция выбора места используется лентой, формой публикации и историями:
`all=true` очищает привязку, даже если страна и город остались в адресе.
Лента страны включает все её города и публикации без города. Лента города
показывает только записи этого города.

В карточке и крупном просмотре есть полоса миниатюр с выделением текущего кадра.
Она прокручивается отдельно от свайпа большого кадра; видео представлены постерами.
Удаление для медиа и историй подтверждается диалогом сайта с ожиданием ответа,
ошибкой и повтором; после успеха показывается «Публикация удалена».

Начальные ограничения: 10 файлов, фото 20 МиБ, видео 90 МиБ и 10 минут. Лимиты
проверяются на сервере; количество и размер — также до отправки. Для изменения
ограничений согласованно обновляются `MEDIA_LIMITS` и `LOCAL_MEDIA_LIMITS`.

## База и окружение

Перед запуском миграций согласовать целевую базу и проверить восстановление
её свежей копии в отдельной БД. Версии `001_legacy` и `002_media_posts` проверены
в локальной БД `travel_media_migration_test` и на восстановленной копии staging.

Отдельная команда из каталога `backend`: `npm run db:migrate` (или `yarn db:migrate`).
Она запускает `node dist/db/migrate.js`. Локально перед этим нужно выполнить
`yarn build` или `npm run build`; после изменения миграций сборку нужно обновить.
В готовом серверном архиве `dist` уже есть, исходники и `ts-node` не требуются.
Использовать нужно сборку той версии, которую собираемся активировать.

Команда требует явно переданный через окружение `DATABASE_URL` и не читает `.env`,
в том числе лежащий рядом с релизом. По умолчанию нужен TLS.
`DB_SSL=disable` использовался для изолированного локального PostgreSQL и при
ручном запуске на VPS через локальный сокет PostgreSQL.
Есть общий журнал версий, ограничение ожидания блокировок 5 секунд и ограничение
времени отдельной команды 120 секунд. Для выпуска задать `DB_MIGRATE_ON_START=false`
и запускать миграцию отдельной командой.

Порядок, по которому выпустили staging:

1. Сделали свежую копию staging 4 ноября, восстановили её в отдельном PostgreSQL
   и дважды прогнали миграцию. Повтор сохранил те же вложения и версии миграций.
2. Вручную запустили миграцию на `travel_staging_final_20261006` от роли
   администратора PostgreSQL. Роли приложения выдали права на четыре новые
   таблицы и проверили их обычным подключением бэкенда.
3. Задали `MEDIA_ENVIRONMENT=staging` в настройках службы.
4. Выпустили бэкенд с выключенным `run_migrations`, проверили старый фронтенд
   с новым API и выпустили фронтенд. Затем проверили старое медиа, историю и
   создание и удаление тестовых публикаций.

Сценарий выпуска staging проверяет `DB_MIGRATE_ON_START=false` по настройкам
systemd и двум файлам `~/travel-secrets/travel-staging-db.env` и
`~/travel-secrets/travel-staging-backend.env`. Флажок `run_migrations` по умолчанию
выключен. Его включение требует отдельного `travel-staging-migrations.env` в
`~/travel-secrets`. Такое подключение на staging не настроено. Сценарий запускает
миграцию до переключения `current` и прекращает выпуск при ошибке.

Если новый бэкенд не запускается или не проходит проверку готовности, сценарий
возвращает прежнюю версию приложения. Расширенная схема базы сохраняется.
Проверка `/api/health` подтверждает доступность процесса. После неё проверяем
чтение ленты и работу с новой схемой. Сценарий выпуска production нужно отдельно
сверить с конфигурацией сервиса перед использованием.

Версия 001 фиксирует существующую схему, версия 002 добавляет таблицы медиа и
переносит старые медиа-записи в одиночные вложения, сохраняя ID, реакции и даты.
Повторный запуск пропускает применённые версии. Старые поля и таблицы не удаляются.

Перед включением новых загрузок явно задать `MEDIA_ENVIRONMENT=staging` или
`MEDIA_ENVIRONMENT=production` на соответствующем сервере. Новые файлы получают
разные префиксы `travel/<окружение>/<автор>/<сессия>/<файл>`. Для разработки
используется `development`, для тестов — `test`. В production-режиме значение
обязательно. Удаление старых файлов из копии production-базы на staging блокируется.

В локальном прогоне использован `MEDIA_ENVIRONMENT=test`; frontend направлен на
локальный backend через игнорируемый Git-файл `.env.local`. Значение `test`
изолирует префикс ресурсов, но загрузки всё равно идут в настоящий Cloudinary.
В режиме динамических папок Cloudinary public ID и папка Media Library
задаются отдельно. Сейчас загрузка не передаёт `asset_folder`. У трёх файлов
стартовой карусели на staging API подтвердил пустое поле папки, поэтому они
отображались в Home. Префикс их public ID — `travel/staging/`.

Для отката приложения сохранены прежние поля обложки, чтобы предыдущая версия
могла показывать карусель как одиночную запись. Триггер БД сохраняет задания удаления
её вложений даже при удалении публикации старой версией; обрабатывать очередь должен
новый backend. При откате приложения новые таблицы сохраняются.
Практическая проверка импорта и отката остаётся перед возможным выпуском на production.

## Ошибки и удаление

При ошибке отдельного файла повтор проверяет уже существующую загрузку и отправляет
только недостающие файлы. При потере ответа публикации форма фиксирует состав и
текст; повтор использует тот же ключ. Отмена после фактически успешной публикации
не удаляет её файлы. Черновики после закрытия страницы не восстанавливаются.

При удалении публикации задания для всех файлов сохраняются в `media_deletions`
в той же транзакции, что и удаление записи. Выполняется первая попытка, затем
автоматические повторы с увеличивающимся интервалом. Перед удалением проверяется,
что ресурс больше не используется. Ошибки и время следующего повтора сохраняются.
Для ADMIN/SUPERADMIN есть `GET /api/media/cleanup` и `POST /api/media/cleanup/retry`;
второй повторяет неудавшиеся удаления сразу и обрабатывает остальные созревшие задания,
сохраняя защитную задержку для ещё не завершившихся загрузок.

Подписанная загрузка Cloudinary может прийти с задержкой. Поэтому после немедленного
удаления остаётся контрольная попытка до завершения двухчасового защитного интервала.
Невостребованные файлы отменённой формы очищаются после этого интервала; брошенная
открытая сессия истекает через 24 часа. Очередь проверяется backend раз в минуту.

## Как повторить автоматические проверки

Обычные проверки: backend `npm test -- --runInBand`, frontend/backend `npm run lint`
и проверка TypeScript. Браузерные сценарии карусели —
`frontend/e2e/media-posts.spec.ts`; они заменяют backend и Cloudinary тестовыми ответами.

Отдельно подготовлен `backend/test/media-posts.e2e-spec.ts`. Он **не использует**
обычный `DATABASE_URL` и пропускается без `MEDIA_TEST_DATABASE_URL`. После разрешения
на изолированную тестовую БД запускается из `backend` командой
`npm run test:e2e -- --runInBand media-posts.e2e-spec.ts`. При локальной БД без TLS
нужен `MEDIA_TEST_DB_SSL=disable`. Тест создаёт и удаляет собственную временную схему,
проверяет перенос и повтор миграции, порядок вложений, отсутствие дублей, счётчики,
реакции и повтор удаления. Настоящий Cloudinary не вызывается.
